# yarn-berry-audit-fix

An experiment in fixing Yarn Berry lockfiles through temporary `resolutions`, with Yarn handling dependency resolution. TypeScript + Vitest, Maven directory layout, no lockgraph dependency.

**Only semver-compatible changes.** For each original dependency request, the temporary resolution selects the lowest published stable version that satisfies the requested range and falls outside every known vulnerable range for that package. The version selected by the install is retained after the temporary rules are removed. Separate major-version branches remain separate. Exact pins and ranges without a compatible fix are reported in `skipped`; there is no `force` mode.

## Why an extra step is needed

The literal `audit → resolutions → install → restore package.json` sequence leaves an inconsistent Berry lockfile, even when the update satisfies the original range. For example:

```text
Original request:     brace-expansion@npm:^1.1.7
Temporary resolution: brace-expansion@npm:1.1.18
After install:        the lockfile has key 1.1.18; key ^1.1.7 is gone
After restoring JSON: yarn install --immutable fails with YN0028
```

The prototype therefore follows these steps:

1. Run `yarn npm audit --all --recursive --json` (with `--no-deprecations` on Yarn 4).
2. Read the flat descriptor table from `yarn.lock`. Query published versions through `yarn npm info`, using the project's registry configuration.
3. Rename the original manifests to adjacent `package.json-<sha256>.backup` files, create working copies, add temporary rules for specific dependency ranges, and run a regular `yarn install`. When `--mode=update-lockfile` is supplied, forward that mode to Yarn to skip linking and building.
4. Restore the original manifests by renaming the backup files back to `package.json`.
5. Patch the lockfile entry headers to restore the original dependency requests, then run the audit again. There is no second install.

`yarn npm audit` is a Yarn Berry command: `npm` names its command group for the npm registry. The prototype invokes Yarn; it does not invoke a separate `npm audit` process.

**Yarn creates package records; the patch changes only their headers.** Fields such as `version`, `resolution`, `dependencies`, `peerDependencies`, and `checksum` remain unchanged. In particular, `resolution:` identifies the selected package version and must not be removed or reset to its previous value. If the operation fails, the entire original lockfile is restored. Integration tests verify that each fix performs one install, preserves the generated package records, and passes a subsequent `install --immutable`, with `--check-resolutions` on Yarn 4.

```diff
-"brace-expansion@npm:1.1.18":
+"brace-expansion@npm:^1.1.7":
   version: 1.1.18
   resolution: "brace-expansion@npm:1.1.18"
```

The patch combines original requests that resolve to the same version and preserves actual exact pins. If an updated parent no longer requires an old range, that descriptor is not restored. To determine this, the patch reads dependency declarations from the records generated by Yarn; it does not traverse the graph or resolve versions again. Records are sorted by their updated headers, matching Yarn's ordering. Ambiguous structures or incompatible results trigger rollback.

Before installation, each original manifest is stored beside its working copy; `sha256` is the full hash of its original contents. Restoring it through rename preserves the original file, permissions, and modification time. The backup disappears after restoration. If the backup path already exists, the operation stops without overwriting it. If restoration fails, the backup is retained and the error includes its path. Dry runs do not create backups.

## Compatibility

By default, the tool installs dependencies into the project. `--mode=update-lockfile` requires Yarn 3+; on Yarn 2, the tool fails before auditing or changing files. Other `--mode` values are rejected.

Pinned CLI versions are installed as npm aliases in `devDependencies`, following lockgraph's approach. The lockfile format version is distinct from the Yarn major version:

| Yarn CLI | Lockfile format | Regular install | `--mode=update-lockfile` |
| --- | --- | --- | --- |
| 2.4.3 | 4 | Yes | Error: unsupported by Yarn |
| 3.1.1 | 5 | Yes | Yes |
| 3.8.7 | 6 | Yes | Yes |
| 4.2.2, 4.13.0 | 8 | Yes | Yes |
| 4.14.1 | 9 | Yes | Yes |
| 4.18.1 | 10 | Yes | Yes |

As of the verification date below, Yarn CLI 5 has not been published: lockgraph's `berry-v5` refers to Yarn 3.1.1 with lockfile format 5. Unknown major versions and prereleases are rejected. Yarn 4.0.0 is excluded because of an audit JSON output bug fixed in 4.0.1. The minimum supported Yarn version is 2.4; the prototype requires Node 22.12+.

Yarn's field is named `resolutions` and has existed since Yarn 2.0. The npm `overrides` field is not used. For Yarn 2/3, the tool supplies selectors both with and without the `npm:` prefix; Yarn 4 normalizes the protocol. Header formats are verified with native `install --immutable`, while record contents are preserved without reserialization.

Yarn 2/3 have a legacy audit limitation: their `audits/quick` request contains only one version per package name. When multiple versions coexist in the graph, advisories for another branch may be omitted or appear only after the first branch is fixed. The prototype reports `warnings` for these graphs, fixes only the advisories it receives, and returns the subsequent audit findings in `remaining`. Regression tests cover this behavior; an empty legacy audit does not establish that every branch is free of known vulnerabilities.

Sources: [manifest/resolutions](https://yarnpkg.com/configuration/manifest#resolutions), [Yarn 2.4](https://yarnpkg.com/blog/release/2.4), [Yarn 2.4.3 install implementation](https://github.com/yarnpkg/berry/blob/%40yarnpkg/cli/2.4.3/packages/plugin-essentials/sources/commands/install.ts), [Yarn 3.0.0 install implementation](https://github.com/yarnpkg/berry/blob/%40yarnpkg/cli/3.0.0/packages/plugin-essentials/sources/commands/install.ts), [audit](https://yarnpkg.com/cli/npm/audit), [official Yarn versions](https://repo.yarnpkg.com/tags).

## Usage

```sh
npm ci
npm run build

node target/main/cli.js --cwd /path/to/project --dry-run
node target/main/cli.js --cwd /path/to/project --json

# Update only the lockfile, preserving the installed tree (Yarn 3+):
node target/main/cli.js --cwd /path/to/project --mode=update-lockfile

# Use a project bundle if yarn in PATH points to Classic:
node target/main/cli.js --cwd /path/to/project --yarn-path /path/to/yarn.cjs
```

`--cwd` must point to the project root containing `package.json` and a Berry `yarn.lock`. By default, the tool invokes `yarn` from PATH, allowing Corepack or the project's `yarnPath` to select the manager. The prototype does not switch package manager versions.

Exit codes: `0` for a clean audit or dry run, `1` when advisories remain, `2` for an execution error, and `130` for interruption. JSON output includes `changes`, `skipped`, `before`, `remaining`, `changed`, `dryRun`, `yarnVersion`, `resolutions`, and `warnings`. During a dry run, `remaining` reflects the initial audit and `changes` contains the proposed plan.

```ts
import { fixAudit } from 'yarn-berry-audit-fix';

const report = await fixAudit({ cwd: '/path/to/project', dryRun: true });
console.log(report.changes, report.skipped, report.warnings);

// Optional mode for Yarn 3+:
await fixAudit({ cwd: '/path/to/project', mode: 'update-lockfile' });
```

## Scope and limitations

- Plain `npm:` semver requests are supported, including scoped packages and combined lockfile keys. Tags, aliases, git, patch, portal, and other protocols are not automatically rewritten. The patch handles headers generated by Yarn 2/3/4; unknown layouts are rejected.
- If an existing user resolution controls a package, that entire package is skipped. Its rule is not replaced with a temporary one.
- Candidate safety is determined by the union of vulnerable ranges in the advisories **received**. This does not prove the absence of every possible vulnerability. The final audit reports remaining or newly discovered issues; the tool performs one pass without an unbounded update loop.
- If installation, auditing, or cancellation interrupts the operation, the lockfile, all workspace manifests, the root `.yarnrc.yml`, and the previous install state are restored. Changes already made to the installed tree during a regular install are not rolled back: run `yarn install` against the restored lockfile after a failure. SIGKILL prevents automatic recovery; original manifests from an interrupted operation remain in adjacent backup files for manual restoration. Run the tool while no other process is modifying the project.
- Regular mode updates the installed tree (`node_modules` or PnP). The `update-lockfile` mode skips linking and building but may download packages and update the cache; the previous install state is restored. In that mode, a subsequent `yarn install` is needed to update the installed tree.
- Standard lifecycle scripts are disabled; third-party Yarn plugins remain part of the project's trusted configuration.
- Manifests are restored, while Yarn itself may normalize lockfile formatting and metadata.

## Tests and directory layout

```sh
# Prepare fixtures and run all checks:
npm run check

# Or prepare fixtures explicitly before running integration tests:
npm run build:test-fixtures
npm run test:integration
```

`build:test-fixtures` reads every external fixture from `src/test/resources/real-world/provenance.json` and prepares its asset under the same `real-world/` directory. Provenance is the only version-controlled file in that directory. It pins GitHub commits, tarball URLs, package versions, registry request bodies, advisory IDs, and SHA-256 hashes.

GitHub files and tarballs are preserved byte for byte. Registry JSON is normalized: metadata includes only declared package versions and installation fields, while audit responses include only declared advisory IDs. The resulting bytes must match the pinned SHA-256 before being saved. New releases and unrelated advisories do not change fixtures; changes to pinned data fail verification instead of silently updating expectations.

All generated assets are ignored by Git, including lockfiles, manifests, licenses, metadata, advisory JSON, and tarballs. Repeated builds verify and reuse cached assets without network requests; missing or corrupt assets are downloaded again. Tests load assets through provenance and check their hashes, reporting `npm run build:test-fixtures` when rebuilding is required. Tests never download fixtures implicitly. `npm run check` runs the fixture build first, so a fresh checkout needs network access for that initial step.

```text
src/main/ts/                         Implementation and CLI
src/test/ts/                         Vitest tests and the fixture builder
src/test/resources/real-world/
  provenance.json                   Sources, recipes, and hashes (version-controlled)
  qiwi/                             Upstream manifests, lockfiles, and licenses (ignored)
  registry/                         npm metadata and tarballs (ignored)
  audit/                            Registry advisory fixtures (ignored)
target/main/                        Compiled JavaScript and declarations
```

Complete lockfiles come from [qiwi/masker](https://github.com/qiwi/masker/tree/1b3cf47948381e82cb775eb450cf7064b82c5d3d) and [qiwi/packasso](https://github.com/qiwi/packasso/tree/74a5f9c1f3d47546d7062028b582763db04064b5). Tests verify the upstream files' SHA-256 hashes and plan changes against the complete lockfiles. Native install tests extract a small `minimatch → brace-expansion → balanced-match/concat-map` subgraph with the original records and checksums. These tests exercise subgraphs rather than building the complete upstream monorepos.

Integration tests run every CLI in the compatibility table against a local HTTP registry on `127.0.0.1`. Package archives are genuine; the audit transport replays a saved advisory snapshot for `brace-expansion`. Once devDependencies and test fixtures are prepared, tests require no external network access. Each CLI generates its own lockfile format from the qiwi subgraph; tests verify `__metadata.version` before and after the fix.

Coverage includes regular `node_modules` and PnP installations, root projects and workspaces, lockfile-only mode with and without an existing installed tree, manifest and Yarn record preservation, one install per pass, repeated audits, idempotence, incompatible pins, and file rollback on failure. Tests also capture legacy audit limitations when multiple versions of a package coexist. Each fix is followed by native `install --immutable` and a byte-for-byte lockfile comparison; Yarn 4 additionally uses `--check-resolutions`.

The matrix is defined in `src/test/ts/pm.ts`; managers are installed locally through `npm ci`. A global Yarn installation is not required.

Verified on 2026-09-29 with Node 24.13.1: `npm run check` passed all 103 tests, type checking, and the build. All 21 real-world assets were rebuilt from provenance and verified; a repeated fixture build reused the cache. The compiled CLI was also checked for `--help`, unknown mode rejection, and rejection of `--mode=update-lockfile` on Yarn 2 without changing input files.
